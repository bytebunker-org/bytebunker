# Frontend: Cloudflare Pages to Workers (2026-10-23)

The frontend is now built as a Cloudflare Worker with static assets. `apps/frontend/wrangler.jsonc` holds the Worker
config (`main` and `assets` point at `.svelte-kit/cloudflare`, which `@sveltejs/adapter-cloudflare` writes during
`vite build`). The repository side is done; the Cloudflare account still serves the old Pages project. Nothing below
has been carried out yet.

## What changes in the dashboard

1. **Create the Worker.** Either run `pnpm --filter @bytebunker/frontend run deploy` once from a machine with the
   production `PUBLIC_*` values (see step 3), or connect the repository under _Workers & Pages → Create → Import a
   repository_ (Workers Builds). The Worker is named `bytebunker-frontend` (from `wrangler.jsonc`).
2. **Workers Builds settings** (if you use Git builds instead of deploying by hand):

    - Root directory: repository root (the frontend needs the pnpm workspace)
    - Build command: `pnpm turbo run build --filter @bytebunker/frontend` (turbo builds the workspace packages the
      frontend imports first)
    - Deploy command: `pnpm --filter @bytebunker/frontend exec wrangler deploy`
    - Production branch: the branch Pages deploys today

    These commands are untested in Workers Builds; check the first build log.

3. **Build-time variables.** The `PUBLIC_*` values are inlined by `vite build` through `$env/static/public`. All
   public ones are committed: `apps/frontend/.env` (defaults, Mapbox username and style ids) and
   `apps/frontend/.env.production` (`PUBLIC_API_BASE_URL=https://bytebunker-api.syscy.de`,
   `PUBLIC_PRODUCTION_COOKIE_DOMAIN=bytebunker.syscy.de`). Only `PUBLIC_MAPBOX_TOKEN` has to be set as a **build**
   variable in Workers Builds (_Settings → Build → Variables and secrets_), not as a Worker runtime variable; copy it
   from the Pages project. Build variables override the committed files, so delete any stale copies of the other
   values from the build settings.
4. **Custom domain.** `wrangler.jsonc` declares `bytebunker.syscy.de` as a custom domain, so the first
   `wrangler deploy` attaches it to the Worker and creates the DNS record. Remove the domain from the Pages project
   (_Custom domains_) and any CNAME to `*.pages.dev` before that deploy, or it fails because the hostname is taken.
   Expect a short gap while the certificate is issued.
5. **Preview deployments.** Pages branch previews do not carry over. If you want them, enable preview URLs for the
   Worker in Workers Builds; `*.workers.dev` stays on by default.
6. **Check, then remove Pages.** Load the site on the custom domain, log in (the session cookie depends on
   `PUBLIC_PRODUCTION_COOKIE_DOMAIN`), and check that `/_app/immutable/*` responses carry
   `Cache-Control: public, immutable`. Then turn off automatic deployments on the Pages project and delete it
   (_Settings → Delete project_).

## Notes

- Compatibility flag: only `nodejs_als` (AsyncLocalStorage for SvelteKit). The SSR bundle imports no other Node
  built-ins. Switch to `nodejs_compat` if a future dependency needs one.
- Observability (Workers Logs) is enabled in `wrangler.jsonc`.
- `_headers` is generated by the adapter and is served by Workers static assets as before. There is no `_redirects`.
- Local check before a deploy: `pnpm --filter @bytebunker/frontend run deploy:dry-run`; run the built Worker locally
  with `pnpm --filter @bytebunker/frontend run preview:worker`.
